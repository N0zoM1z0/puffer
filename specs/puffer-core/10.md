# Tool Error Continuation

## Purpose

Keep provider-driven tool rounds alive when one runtime tool invocation fails,
so the model can observe the failure and choose a fallback action.

## Design

The serial tool-batch path now mirrors the mixed/parallel path: execution
errors are converted into a tool invocation with `success = false`,
`terminate = false`, and an output string prefixed with
`Tool execution failed:`. The agent loop then serializes that invocation as
the provider-specific tool result in the next request.

## Logic

A single failed tool call previously returned an error from the batch executor
and aborted the provider turn. This made recoverable runtime failures, such as
reading a missing file, appear as top-level provider failures in the TUI.
Returning a failed tool result preserves the conversation contract and lets the
provider continue from the observed tool error.

## Contracts

- Successful serial tool calls keep their existing stdout/stderr merging,
  success flag, termination metadata, and result-budget processing.
- Failed serial tool calls are recorded as normal tool invocations with
  `success = false`.
- Anthropic continuation requests include the failed call as a `tool_result`
  with `is_error = true`.
- The mixed/parallel tool path behavior is unchanged.

## Compatibility

This aligns single-tool Anthropic turns with existing OpenAI tool-error
handling and with the existing parallel batch behavior. User-facing sessions no
longer fail the entire turn solely because a requested file path does not
exist.
